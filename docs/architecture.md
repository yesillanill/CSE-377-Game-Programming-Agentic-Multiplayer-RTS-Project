# AI Strategic Commander & in-game chat — architecture

The bottom HUD has a chat panel on the right. Two icon tabs sit in a vertical rail on its left
(`Assets/Art/UI/Icons`: person = **Player**, robot = **AI Commander**):

* **Player** — text chat with the opponent over Photon PUN (`PhotonNetwork.RaiseEvent`, event code 120).
* **AI Commander** — the agentic advisor required by the project (MCP + LLM + RAG + structured plans + human approval).
  A small dot on the robot icon shows the AI state (amber starting, green ready, red failed).

The panel replaced the old multi-selection icon grid; the command panel moved left next to the selection card.
The icons are dark navy, so the tab buttons use a light background (gold when active) instead of tinting the icon.

## Data flow

```
Player types a question (AI tab)
  │
  ▼
Unity: AiSnapshotBuilder.Build()  ── fog-of-war filter happens HERE (VisibilityService) ──
  │   own resources / population / units / buildings / upgrades / recent own events
  │   + ONLY enemies visible right now. No field exists for opponent economy, tech or hidden units.
  ▼
AiGatewayClient  POST http://127.0.0.1:8765/v1/ask   header X-RTS-Session: <random per-match token>
  ▼
AI Gateway (ai/gateway, FastAPI, binds 127.0.0.1 only)
  │  pydantic validation (extra fields rejected), session token bound to one match_id, 1 request at a time
  ▼
StrategicCommander agent (ai/agent/agent_runner.py)
  │  1. code guard: language (TR/EN), cheat / prompt-injection patterns, greeting
  │  2. LLM router (Ollama llama3.1:8b, JSON-schema constrained): category + tools chosen from MCP list_tools()
  │  3. MCP client → custom MCP server (ai/mcp_server/server.py, official MCP Python SDK, in-memory transport)
  │        get_player_resources · get_army_status · get_visible_enemies · get_technology_status
  │        get_recent_events · estimate_plan_cost · search_game_knowledge (RAG)
  │  4. LLM answer over tool results (passed as untrusted DATA), may request more tools (bounded loop)
  │  5. ActionPlan: normalize names → JSON Schema validation → gameplay pre-check (mirror of GameActionValidator)
  ▼
Unity: answer + tool/source log shown in chat; AiPlanSchema re-validates the plan; plan card with APPROVE / REJECT
  │
  ├── REJECT → logged, no game state change
  └── APPROVE → AiPlanExecutor → GameCommands.RequestTrainUnit / RequestResearch / RequestBuild / RequestMove
                → GameActionValidator re-checks the LIVE state → Photon (same path as a button click)
```

## Why each piece exists

| Requirement (project PDF) | Where |
|---|---|
| ≥5 custom MCP tools, ≥3 live-state | `ai/mcp_server/server.py` (7 tools, 5 live-state) |
| Tool test with valid/invalid input | `ai/tests/test_mcp_tools.py` (real MCP client session) |
| Dynamic tool calling, not hard-coded order | router picks tools from `list_tools()`; `ai/tests/test_agent_loop.py` |
| Step limit, tool log, limited confidence on failure | `MAX_AGENT_STEPS=4`, `MAX_TOOL_CALLS=8`; `ai/logs/agent_*.jsonl`; `limited_confidence` |
| RAG with source ids | `ai/rag/` (36 chunks: 4 units, 9 buildings, 9 techs, 14 rules/strategy), BM25 + TR→EN synonyms |
| JSON Schema ActionPlan | `ai/agent/schemas/action_plan.schema.json`, mirrored in `AiPlanSchema.cs` |
| Human-in-the-loop | `AiPlanCardView` + `ChatPanelController.ApprovePlan/RejectPlan` |
| Validate twice | gateway schema + pre-check; Unity schema; `GameActionValidator` on approve |
| Fog-of-war never reaches the LLM | `AiSnapshotBuilder` + `SafeSnapshot(extra="forbid")` |
| Identity never from the model | tools take no player/match id; session bound by header; extra args dropped & logged |
| Prompt-injection resistance | `agent/guard.py` + code-written cheat answer; `ai/logs/security_*.jsonl` |
| Off-topic refusal, answer in user's language | guard + router category + `on_topic` field; language detection + fix-up pass |
| Evaluation | `evaluation/` (prompts, snapshots, `run_eval.py`, results, summary) |

## Security model

1. **Filter before the model.** The full world state never leaves Unity. `AiSnapshotBuilder` copies only the
   local player's own state and `VisibilityService.GetVisibleEnemies / GetVisibleEnemyBuildings` (cells that are
   Visible right now). Enemy deaths are recorded as events only when the cell is visible.
2. **Strict schema at the boundary.** The gateway rejects unknown fields (e.g. `enemy_resources`) with HTTP 422
   and writes a security log entry that contains only the field location, never the submitted value.
3. **No identity from text.** No tool has a `player_id`/`match_id` parameter. The per-match token is generated by
   Unity, bound to the first `match_id`, and only its hash is logged. The LLM never sees it.
4. **Read-only tools, allow-list.** All MCP tools are annotated read-only. The agent only calls tools that appear
   in `list_tools()` *and* the allow-list; arguments not in the tool's input schema are dropped and logged.
   No filesystem / shell / HTTP / code tools exist.
5. **Prompt injection.** Tool results and retrieved knowledge are sent in a message labelled as untrusted data.
   Requests for hidden information are detected in code (TR + EN patterns) and answered by code using only
   `get_visible_enemies`, so the model cannot invent hidden details or produce a plan for such a request.
6. **Actions.** The LLM can only *propose*. Unity filters the plan by schema, shows it, and executes only after
   APPROVE, through `GameCommands`, which calls `GameActionValidator` on the live state.
7. **Chat.** Player names come from Photon's authenticated sender id, not from the payload; text is length
   limited, control characters are removed and the message is rendered inside `<noparse>`.

## Unity components (all pre-placed in `Game.unity` by the editor tool)

| Object | Components |
|---|---|
| `HUD_Canvas/BottomPanel/ChatPanel` | `ChatPanelController`, tabs, two `ScrollRect` logs, `TMP_InputField`, send button |
| `HUD_Canvas/BottomPanel/ChatTabRail` | `PlayerTabButton`, `AiTabButton` (icon, active bar, unread badge, AI status dot) |
| `AI_Systems` (scene root) | `AiGatewayClient`, `AiGatewayLauncher`, `PlayerChatService`, `AiEventRecorder` |
| `Assets/Prefabs/UI/ChatMessage.prefab` | one chat line (`ChatMessageView`) |
| `Assets/Prefabs/UI/AiPlanCard.prefab` | plan approval card (`AiPlanCardView`) |

Only message lines and plan cards are instantiated at runtime (they are content).
Built by **Tools ▸ RTS ▸ Setup Chat Panel (Player + AI Commander)**, which runs the UI theme pipeline
(`RTSUIThemeTools`) so generated sprites are saved as assets. Re-running is safe (idempotent).

Keyboard: **Enter** focuses the input / sends, **Esc** leaves the input, **Tab** switches tabs. While typing,
WASD camera movement and Esc shortcuts are ignored (`UIInputGuard`).

## Automatic start-up

`AiGatewayLauncher` checks `/health` when the Game scene starts. If needed it starts `ollama serve` and
`ai/start_gateway.bat` as hidden processes (fixed local paths only, no player input in any command line), waits for
`/health`, and verifies that the model is installed. The gateway receives `RTS_PARENT_PID` and exits when that
process ends, so closing the game or the Editor (or a crash) leaves no orphan server. A failed start is retried when
the player asks the next question.

## Multiplayer note

AI plans run through the same authority path as the player's own buttons, so they synchronise exactly like manual
commands. Each player's AI only sees that player's own fog-filtered view; the gateway runs on each player's
own computer.

## Known limitations

* `llama3.1:8b` on a 6 GB laptop GPU: about 7 s mean / 14 s worst latency per question.
* Small-model reasoning mistakes are possible (e.g. proposing a building the player already has). The
  pre-check and `GameActionValidator` stop illegal actions; they do not judge strategic quality.
* Tool selection misses occur (see `evaluation/summary.md`, case C02).
* `BUILD` picks the first valid site around the Town Center automatically.
